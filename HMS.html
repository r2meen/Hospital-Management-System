Chapter 01

The Problem & Motivation

🏥 Introduction

The Hospital Management System (HMS) automates and simplifies daily hospital operations — handling patient registration, doctor scheduling, appointments, and billing — while reducing paperwork and human error through a user-friendly, menu-driven interface.

⚠️ The Problem

Many hospitals still depend on manual record-keeping via paper files. This approach is slow, error-prone, and leads to data misplacement. Searching patient history, updating records, or checking doctor availability becomes painfully time-consuming.

💡 Motivation

To reduce the burden of manual workflows and enable a more efficient system for small and medium healthcare facilities that need organized structure but cannot afford complex software solutions.

🧩 Key Challenge

Integrating all modules — patient, doctor, appointment, and billing — into one seamless system. Ensuring proper function communication, input validation, clean menu flow, and preventing crashes from invalid input required careful debugging and planning.

Primary Beneficiaries
🗂️
Hospital Administrators
Manage all records efficiently with fast search, update, and delete operations.
👨‍⚕️
Doctors
Access patient information instantly, matched by disease and specialty.
🧑‍🤝‍🧑
Patients
Faster registration and significantly reduced waiting time.
💳
Billing Staff
Generates accurate bills instantly with automated tax, discount, and payment calculations.
Distinguishing Features
F1 Clear, structured, menu-driven interface with multi-level navigation
F2 Four fully integrated modules: Patient, Doctor, Appointments, Billing
F3 Comprehensive input validation preventing invalid entries and crashes
F4 Permanent file-based storage (.txt) for data retention across sessions
F5 Automated billing with tax, discount, and dual payment method handling
F6 New C skills applied: fopen/fprintf/fscanf, structs, modular functions
Chapter 02

Methodology & Design

01

Requirements Analysis

Identified all essential features: patient management, doctor management, appointments, billing, and file-based record storage. Mapped out every user-facing operation from first principles.

02

System Structure Design

Designed overall architecture, menu structure, data flow, and module interactions. Flowcharts and algorithms helped visualize system logic before a single line of code was written.

03

Data Structure Creation

Defined struct templates for storing Patient and Doctor information. Planned text file layouts (patients.txt, doctors.txt, appointments.txt) for saving data.

04

Module Development

Coded each module separately using dedicated functions, ensuring input validation and robust error handling were built in from the start — not bolted on afterwards.

05

File Handling Implementation

Integrated file operations using fopen(), fprintf(), fscanf(), fclose() to permanently store and retrieve records. Temporary files used during updates to prevent data corruption.

06

Testing & Debugging

Tested using various inputs and corrected logic errors, file operation issues, and input-related crashes. Manual testing with diverse test cases across all modules.

07

Final Integration & Formatting

Combined all modules into a single comprehensive system with clean, consistent output formatting and a unified switch-case main menu as the central hub.

Key Algorithms

Add Patient — Algorithm

  1. Ask user to input Patient ID → check for duplicate via checkDuplicateID()
  2. Input details: first name, last name, age, gender, disease
  3. Disease-based doctor matching — show relevant doctors, let user assign
  4. Concatenate full name (firstName + lastName)
  5. Confirm → append data to patients.txt

Billing Module — Algorithm

  1. Input Patient ID → load patient + doctor details
  2. Input room type → map to daily rate (General Ward / Semi-Private / Private / ICU)
  3. Input days stayed → roomCharge × days
  4. Select lab test → calculate testFee
  5. Subtotal = roomCharge + doctorFee + testFee
  6. Apply 5% tax and fixed 500 discount
  7. Handle payment: Cash → calculate change, Card → confirm
  8. Display formatted hospital bill

File Safety Strategy

  • Update / Delete operations never modify files in-place
  • All records except the target are written to a temporary file
  • Original file is replaced with the temp file only after confirmation
  • This prevents data corruption if the operation is interrupted
